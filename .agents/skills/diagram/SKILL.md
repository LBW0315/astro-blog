# BUNBOUの図解作成

Claude Codeが書いた記事MDXを受け取り、記事中の図解マーカーを実際の図解コンポーネントに置き換える。

## 入力

対象記事のパス（例：`src/content/blog/2026-09-23-foo.mdx`）。
記事の中には、図解を入れたい位置に次の形のマーカーが置かれている。

```
{/* DIAGRAM: 名前 — 何を説明する図か / 入れたい要素 */}
```

## やること・やらないこと

**やること**

- マーカーの位置に合う図解コンポーネントを `src/components/diagrams/` に作る。
- マーカー行を、そのコンポーネントの呼び出しに置き換える。
- MDX冒頭のimport文を、既存記事と同じ書き方で追加する。

**やらないこと（重要）**

- 本文の文章には一切手を触れない。言い回し、誤字、見出し、frontmatterも直さない。文章の指摘は最後の報告にまとめて書くだけにする。
- マーカー以外の場所に図を増やさない。
- ラスター画像（PNG/JPEG）は作らない。記事内の絵はすべてSVGコンポーネントで表現する。
- 新しいパッケージは入れない。必要になったら止めて相談する。

## 作り方

- まず `src/components/diagrams/` の既存コンポーネントを読み、作りと書き方を揃える。特に `AwsBlogArchitecture.astro` と `DeployFlow.astro` を参考にする。
- 既存のコンポーネントで足りるものがあれば、新しく作らずそれを使う。
- 他の記事でも使い回せそうな汎用部品を新しく足す場合は、実装前に案を出して確認を取る。
- 図やイラストには、内容がわかるアクセシブルな名前（`aria-label` または `aria-labelledby`、`<img>`なら`alt`）を必ず付ける。

## タッチ：手描き風・アナログ感で統一する

BUNBOU（文房具）らしい、ノートにペンで描いたような図にする。ただし読みやすさが最優先。

- 線と図形は手描き風にする
  - SVGフィルター（feTurbulence + feDisplacementMap）で、線と図形だけに控えめなゆらぎをかける（目安：scale 3 程度）
  - フィルターのidは記事内で重ならない名前にする
  - アイコンも、少ない線で描いたシンプルな線画にする（公式サービスアイコンは使わない）
- 文字にはゆらぎをかけない。手書き風フォントも使わず、サイトの見出し・本文フォントのままにする
- 表（比較表・料金表など）は絵にせず、Markdownの表にする（読み上げ・コピーができるように）。マーカーが表を求めている場合は、SVGにせずMarkdownの表を置き、そう報告する
- 飾りだけの絵は増やさない。図の要素は絞り、ラベルは指す物のすぐ近くに置き、読む順番は矢印で一本道にする
- 線と色の意味は、記事をまたいで統一する
  - 青磁の実線：できている・完成している部分
  - 灰桜の点線＋「これから」のラベル：これから作る・予定の部分
- スマホ幅（375px程度）で図の文字が小さくなりすぎないか確認する（図の中の文字は14px以上が目安）

## 色

- 分類や図解の色分けには、理解を促すためなら積極的に色を使ってよい
- 色はサイトのデザイントークン（CSS変数）から使い、コンポーネントに色コードを直接書かない
  - 足りない色があれば、勝手に足さず、デザイントークンへの追加を提案する
- 視認性を最優先する
  - 文字と背景のコントラスト比はWCAG AAを満たす
  - ライトモード・ダークモードの両方で読めることを確認する
  - 色だけで意味を伝えない（アイコン・ラベル・線の種類なども併用する）
- 1つの図で使う色は3色程度までに抑える

## 確認

- `npm run build` が通ることを確認する。
- デスクトップ幅と375px程度のスマホ幅、ライトモードとダークモードで崩れていないかを確認する。開発サーバーを使う場合は `AGENTS.md` に従って `astro dev --background` で起動し、確認後に停止する。
