# BUNBOUの記事チェック

Claude Codeが書いた記事を、公開前に第三者の目で点検する。

## 入力

対象記事のパス（例：`src/content/blog/2026-09-23-foo.mdx`）。

## 絶対に守ること

**ファイルを書き換えない。** 見つけたことは指摘と修正案として出力するだけにする。採用するかどうかは書き手が決める。

**書き手の言い回しを尊重する。** 明らかな誤りでない限り、文体・語り口・個人的な言い回しは「直すべき」として挙げない。整った文章にすることが目的ではなく、公開して困ることを見つけるのが目的。

## 見るところ

### 必ず見る
- 誤字脱字、変換ミス
- 表記ゆれ（例：同じ記事内での「スマホ」と「スマートフォン」の混在）
- 事実として間違っていること、古くなっていること（手順、価格、サービス名、仕様）
- 個人情報（家族の名前、住所や勤務先がわかる記述、写り込み）
- リンク切れ、リンク先が意図と合っているか
- コードブロックの言語指定、コードが実際に動くか
- 図やイラストにアクセシブルな名前（`alt` / `aria-label`）があるか
- frontmatter：`title`、`description`、`category`、`pubDate` が内容と合っているか
  - ファイル名は `YYYY-MM-DD-slug.mdx` で、日付が `pubDate` と一致しているか

### 読み手目線で見る
- 前提の説明が飛んでいて、初見の読者がつまずくところ
- 結論や「で、どうすればいいか」が書かれていないところ
- 同じことを二度言っている箇所

### 見ないもの
- 文体・語り口の好み
- SVG図解の作り込み（これは `$diagram` の担当）

## 出力の形

そのまま読んで判断できるように、重要度で分けて出す。

```
## 要修正（公開前に直したい）
- [ファイル:行] 何が問題か → 修正案

## 提案（直すかは任せる）
- [ファイル:行] 気になった点 → 案

## 確認してほしいこと
- 自分では判断できなかったこと（事実確認が必要な数字、意図が読み取れなかった箇所など）

## 問題なし
- チェックしたが問題がなかった項目
```

指摘が一件もない項目は省かず、「問題なし」にまとめて書く。何を見たのかが分かるようにする。
